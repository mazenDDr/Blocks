# ADR 0024: Transactional native agent conversations in local serving

Status: accepted. Builds on ADR 0008 (native agents), 0012 (local production) and 0023 (isolated turns).

1. **Separate versioned adapter.** `conversation_adapter.py` registers completed END graphs as `__agent_conversation__`. Require thread-scoped state and turn-scoped HTTP text inputs. Preserve the ADR 0023 adapter bytes and all other registered serving-family identities. Existing stateless versions continue to verify; no training or dependency installation is required. The bounded validation/execution wrapper is versioned separately so expanding conversation scope does not silently change existing manifests. Both adapters use the original native compiler, reducers, blocks and input-reset semantics. Tools, effects, interrupts, retrieval, memory policies/indexes and remote/fixture providers remain refused. All ADR 0023 graph/state/input/context/model/budget bounds apply; serialized checkpoints add a 128 KiB limit.
2. **Native checkpoints, not reconstructed state.** Execute each turn in a temporary store and isolated native `InMemorySaver`. Restore the previous END checkpoint with its channel values, channel versions, versions seen and native metadata using the installed saver’s serializer/put interface. Pickle fallback is disabled by the native serializer default. Only application-produced, SHA-verified CAS snapshots are consumed; no uploaded checkpoint/deserialization endpoint. Native `build_input(..., thread_exists=True)` resets turn-scoped channels with `Overwrite` and preserves thread channels. A fresh execution ID per turn and stable native thread ID per conversation carry provenance. Original research checkpoints/history are never copied or mutated. Save only the latest END snapshot, not intermediate tasks or an unbounded historical saver. Native graph reducers own any declared history window; exceeding global bounds refuses the turn, never silently truncates it.
3. **Success commits atomically.** Add `agent_sessions(scope,revision,checkpoint,last)` to production SQLite. Scope is release/user/session, where user/session are caller-declared isolation keys, not authenticated principals. Require an explicit session; maxBatch=1 and sessionMode=conversation. The owning runtime serializes each scope; different scopes can run concurrently within existing admission limits. Snapshot candidate is immutable CAS; its expected parent revision/hash is checked under `BEGIN IMMEDIATE`. Cancellation and deadline are checked before any durable head update, including after snapshot/trace serialization. Successful head/revision and request trace pointers commit together. Native inference, cancellation, budget exhaustion, schema/integrity errors, stale parents, deadline expiry and transaction failure never advance the head. Immutable orphan bytes after failed writes are possible; retention/GC is not implemented.
4. **Crash and retry behavior.** One owning control process only. Restart marks unfinished requests failed (`E_SERVING_RESTART`), does not resume a task or repeat a model call, and preserves the last successful checkpoint. A duplicate committed request returns its original trace without another turn; conflicting input/release remains refused. A request committed before disconnect stays successful and cannot be cancelled afterwards. Rollout creates a separate release scope; rollback resumes that older release’s existing conversation. No automatic migration between versions/releases. Tests kill a real process after native inference and before commit, and force a SQLite trace-write failure after the checkpoint update; both preserve the last committed head. CAS parent checks are defensive consistency guards, not a distributed serving claim.
5. **Persistence versus trace capture.** Conversation mode necessarily persists native state/history even with captureInputs=false. Release policy, API and editor state this explicitly. Full model contexts/state/events in request traces still require captureInputs=true; output text and hashes/usage remain recorded otherwise. Checkpoint inspection is read-only, verifies the pinned version and snapshot, and exposes actual state with release/version/user/session/revision/hash provenance. Shared token protection applies when configured, but there are no accounts, roles, session ownership enforcement or encryption.
6. **Exact prior-state replay.** Successful/candidate traces record the immutable parent revision/hash before execution. Captured replay restores that exact prior checkpoint in an isolated saver, makes a new native model call if the graph has one, and discards its candidate; it never uses today’s live head or advances it. Missing inputs or a missing parent record refuses replay. Recorded provider requests, source segments and actual responses/usage remain inspectable. Monitoring reads warmup/traces and never runs an LLM; single-reference length comparisons and literal agreement with separately supplied labels retain ADR 0023’s limited interpretation. A conversation response distribution depends on history as well as current input; current-input length drift does not measure history or semantic quality.
7. **Working journeys.** `serving_conversation` uses explicitly SYNTHETIC teaching prompts and real local Ollama, retaining the last six native messages. Source run → registration → isolated warmup → two same-session turns → checkpoint/context inspection → parent replay → native HTTP traffic → release isolation/rollback are runnable. Native offline tests compare complete states against the independent research saver and exercise concurrency, failure, rollback, restart and integrity. A live test proves actual prior user/assistant messages are sent, a new session starts fresh and restart preserves history. Real Chrome verifies the editor controls and captured native values.

Remaining scope: checkpoint deletion/reset/fork/migration/retention APIs; authenticated conversation ownership; retrieval/index/memory/effect dependencies and approvals; streaming, multiple/structured model nodes and external providers; distributed execution and broader workloads. There is no semantic-answer accuracy claim from the teaching prompts.
